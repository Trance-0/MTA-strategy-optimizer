# 工作区总览与现状评价

本仓库不是单一源码目录，而是“一个当前业务实现 + 一套本地 Agent/BMad
工具链 + 项目知识与历史记录”的复合工作区。业务能力评价只针对
[`modules/amc_mta`](../modules/amc_mta/README.md)；其余目录按工具、文档、
研究和追溯资产评价，不被误算成产品能力。

## 结论

当前工作区整体处于**结构清楚、可复现、适合继续研发，但业务模型仍是验证型
Demo**的状态。

- AMC MTA 的代码、输入、五份输出、文档和 100 项测试一致，流水线可确定性复现。
- 项目当前事实、历史愿景、外部研究和实现记录已经分区，不再把未实现功能描述为
  当前能力。
- `.agents` 与 `_bmad` 是安装型开发工具，不是营销产品源码；119 个已声明技能与
  119 个直接技能目录完全对应。
- 工作区没有空文件、符号链接、缓存字节码、临时文件或未归位业务文件。
- 41 份非规格项目 Markdown 全部可从根入口到达且没有本地断链；94 个 Python 文件和 7 个 JavaScript
  文件均通过语法检查。
- 工具层存在一个已确认的上游测试断言不一致；另有一个工具测试依赖 `pytest`，
  当前环境未安装，因此没有执行。两项都不影响 AMC MTA 运行。

## 分区评价

### 业务实现：`modules/amc_mta`

定位为 AMC 匿名聚合路径上的五段多触点归因诊断 Demo。当前优势是契约清楚、
输出完整、Markov 与 Path-level Shapley 双模型治理逻辑明确、测试覆盖较强。
主要限制是使用模拟数据、没有滚动窗口与重采样稳定性证据、没有真实 AMC
隐私执行验证，也不具备因果增量或自动预算能力。

详细评价见 [AMC MTA 能力评价](amc_mta/amc-mta-capability-assessment.md)。

### 项目知识：`docs`

当前事实、模块架构、能力边界、研究原件和历史愿景已分层；位置规则见
[工作区文件位置管理](workspace-file-management.md)。8 份 PDF、2 份 DOCX
和 Amazon Ads OpenAPI JSON 是研究输入，不是运行依赖。最大文件为 15.1 MiB 的
机器学习论文 PDF，保留合理。

### 历史追溯：`design-artifacts` 与 `_bmad-output`

两处内容有明确用途：

- `design-artifacts` 保存早期营销投放优化平台愿景；
- `_bmad-output` 保存已完成整改规格和延期事项。

它们不应删除，也不能覆盖当前源码与契约。旧规格中出现四段粒度、`units_sold`
或已删除的 `modules/mta` 属于历史语境，不是当前残留实现。

### 开发工具：`.agents` 与 `_bmad`

这是 BMad 6.8.0 及其扩展模块的安装结果：

- Core/BMM：6.8.0；
- TEA：v1.19.0；
- BMad Builder：v2.0.0；
- Automator：`main` 渠道；
- CIS：v0.2.1；
- GDS：v0.6.0；
- WDS：v0.4.3。

127 组相同内容主要是测试架构技能为独立分发而复制的知识文件，不是应删除的
普通重复文件。模板中的占位链接、占位 TOML 和 `TODO` 示例也属于生成器输入，
不能按业务文档规则直接清理。

## 风险与优先级

1. **先补模型证据**：真实 AMC 可执行 SQL、滚动窗口、重采样和模型稳定性验证。
2. **再补工程基线**：依赖锁定、统一测试入口和 CI；当前仓库没有 CI/CD 或部署配置。
3. **工具问题隔离处理**：不要为修复上游技能测试而改动 AMC MTA。若确实使用
   standalone module scaffold，再单独修复插件命名契约并补齐 `pytest` 测试环境。
4. **保持分区边界**：当前事实以运行代码和模块契约为准；研究、历史愿景和旧规格
   继续只用于追溯。
