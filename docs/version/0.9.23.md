# Version 0.9.23

Date: 2026-08-20

## Changes

- Added a Form view to Budget Manager's Add/Edit modal, alongside the existing JSON editor rather than replacing it. `masterObjectFields.js` declares each section's fields against the canonical vocabulary in `modules/mta_common/src/enums.py` and `provider_capabilities.py`: `provider`, the four `_availability` fields, and `margin_source` carry a real `StrEnum`; `ad_product`, `billing_type`, and `currency` carry a suggested but unenforced vocabulary; everything else — `status`, `category`, `brand`, `format`, `placement`, `creative` — is a free string with no closed set in the data model. `MasterObjectForm.vue` renders one field per row: a plain input for free text, a three-way select for a boolean, a chip list with a search-filterable add field for a multiselect (`supported_ad_products`, `supported_interactions`), and for every enum-backed or suggested field a native `<input list>` bound to a `<datalist>` — a type-to-filter dropdown that still accepts a value the list does not carry, since the server enforces no field-level vocabulary at all. Every kind of field lands on one input pattern a non-technical reader already knows from an address form's country selector, rather than a form that mixes hard locks with free text unpredictably.
- Fixed the JSON editor opening on a bare `{}` for a new record. `openEditor()` now merges the new record over `buildTemplate(sectionKey)`, so both the Form and the JSON view start from every valid field already present with its default, and switching between the two views serializes or parses explicitly at the moment of the switch rather than keeping two representations live at once.
- Diagnosed a production deploy failure in which a freshly activated release, and then the rollback to the previously active release, both failed `deploy_worker.sh`'s health check — a symptom no per-release code difference could produce, since a rollback restores code that was already running successfully. The cause was `dashboard_healthy()` gating activation on `GET /api/dashboard`, which returns `503` whenever the database configured in `${ETC_ROOT}/dashboard.env` is unreachable or `attribution_result` is empty; that setting is host-level and shared across every release, so any release deployed to that host would fail identically regardless of which commit it ran. Added `GET /api/health`, a liveness route independent of `DATABASE`/`PG_*` and of the database already holding rows, and repointed `dashboard_healthy()` at it. A release with no data loaded yet is now a successfully deployed release; database readiness remains visible in the running dashboard as the page-level `database_unavailable` state `/api/dashboard` already reported.

## Verification

- `npm test`: 47 dashboard tests pass, including the existing server-startup test extended to assert `GET /api/health` returns `200` with `{ok: true}` ahead of the existing `/api/dashboard` and master-write assertions.
- `npm run build` succeeds; started the built server locally against a real PostgreSQL instance and confirmed `/`, `/api/health`, and `/api/dashboard` each answer `200`.
- Confirmed `git status` carries no `dashboard/dist` entry after a local build — the existing unanchored `dist/` rule in `.gitignore` already covers it.
- Updated `docs/en/dashboard/deployment.md` and `docs/en/dashboard/index.md` so the documented health check and route contract match the new liveness/readiness split.

## Notes

- The Form view and the JSON view stay two renderings of one plain object (`editorRecord`); no field the JSON editor can express is unreachable from the Form view, since an unrecognized or future field simply has no declared row and is preserved on save.
- The health check's previous coupling to `/api/dashboard` was silent: `dashboard_healthy()` never logged which of its two probes failed, so the journal excerpt that surfaced this looked identical for a real code regression and for an unreachable database. That ambiguity is now structural rather than diagnostic — the two concerns have separate routes — rather than fixed by adding more logging to a check that was answering the wrong question.
