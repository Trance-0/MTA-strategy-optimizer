# Version 0.9.57

Date: 2026-09-10

## Changes

- Replaced `docs/en/strategy-recommendation/campaign-budget-optimizer.md`
  with a five-page directory that specifies the Campaign response model and
  optimizer at reproduction grain: model and assumptions, data collection and
  data model, fitting implementation, optimizer implementation, and output
  artifact.
- Removed the numbered prefix from every heading under
  `docs/en/strategy-recommendation/`, and repaired the three inbound anchor
  links and sixteen inbound page links that change made stale.
- Gave every page in the section an `order` frontmatter value and turned on
  `sortMenusByFrontmatterOrder` for its sidebar block, so the sidebar follows
  reading order rather than filename order.
- Corrected three statements the old page carried: the test count is 116, not
  115; the generated artifact is deliberately committed rather than never
  committed; and the command-line and backend callers build the Initial
  Strategy differently, which the backend's own docstring claims they do not.

## Why the old page could not be reproduced from

The old page was 326 lines covering five source files, and it read as an
orientation document: it stated what the optimizer does and named the classes
involved, but a reader could not rebuild the implementation from it. It gave
the functional forms without the search grids that fit them, described the
shadow-price solver without either bisection, and listed the artifact's keys
without their values or their tolerances.

Every claim in the replacement is grounded in freshly-read source or in the
committed artifact. Both bisections, `_search_ceiling`, the remainder
distribution, and the post-validation tolerances are decomposed line by line in
the same `#### Line N` form the attribution pages use, each line carrying what
it maps to in the algorithm and why it is written that way. The worked examples
compute real numbers from the committed parameters rather than illustrating
with invented ones.

The five pages answer, in order, the seven questions a specification of a
fitted model has to answer: what model, what assumptions, how the data is
collected for prediction, what data model, how it is implemented, where the
intermediate product is saved, and what the outcome is. The parent `index.md`
states why the pipeline divides this way — each stage has a distinct contract,
a distinct failure mode, and a distinct thing it is allowed to know.

## Why the heading numbers had to go

The numbers had stopped describing anything. `current-budget-calculation/`
carried one global sequence spread across four files, so its `index.md` held
section 1, `inputs-and-scores.md` held 2 through 8, `groups-and-output.md` held
9 through 14, and `boundaries-and-locations.md` held 15 and 16 — a reader
opening any child page found it starting at an arbitrary number.
`current-implementation.md` was worse: it carried two independent `### 1.`
through `### 8.` sequences on the same page, because a split had left two
numbered lists sharing one file.

Removing them exposed two headings that existed only to hold a number, and one
sentence per page that introduced a list which no longer followed it. Those are
folded into the paragraphs they belonged to.

Three inbound anchors depended on the numbering. Two pointed at
`#1-verify-evidence-lineage-before-calculation` and now point at the unnumbered
anchor; the third pointed at `#4-ad-group-output` on a page that has no such
heading and never did, and now resolves to the output data contract that owns
it.

## The three corrections

The test count was stated as 115. Running each of the module's five test files
gives 26, 18, 28, 10, and 34, which is 116.

The old page stated the artifact "is a generated file and is never committed".
`.gitignore` ignores `modules/*/outputs/` but negates
`campaign_strategy.json` and `initial_budget_recommendation.json` explicitly,
so both are tracked deliberately — the evaluation tests read them as fixtures.
The sentence was the wrong side of that disagreement, not the artifacts.

The third is drift the documentation records rather than resolves.
`generate_campaign_strategy.py` builds each Campaign's initial budget from the
latest row's recorded `baseline_budget` and emits the key `basis`;
`backend/services/models.py` averages every configured budget the Campaign was
observed at and emits `allocation_basis`, while its docstring says it "Mirrors
what `generate_campaign_strategy.py` builds, so the two agree." Because that
figure is the default authorized budget, the two callers can authorize
different totals from the same snapshot. Which side is authoritative is a code
decision, so the output artifact page states the divergence and leaves it.

## Limits

The specification describes the implementation as it stands; it does not
validate the model. Whether a two-stage exponential is the right functional
form, and whether maximizing the fitted curves raises realized revenue, are
questions for a compliant experiment, and both pages say so rather than
implying the fit answers them.

The Initial Strategy divergence between the two callers is recorded, not fixed.
Until it is, a plan produced through the dashboard's model endpoint and one
produced by the command can differ for the same input.
