# Version 0.9.55

Date: 2026-09-10

## Changes

- Pointed every reader of the pipeline output directory at an empty tree for the
  snapshot contract tests, so they measure this repository rather than whatever
  the deployment machine generated on an earlier run.
- Anchored each deployment synchronization exclusion to the one location its
  state occupies, so the live tree again matches the published snapshot.
- Promoted a surviving stale directory from a log line to a deployment failure.

## The defects

Both faults share a cause: a host keeps state between deployments, and both the
test suite and the synchronization step treated leftover state as authoritative.

### The suite read the machine, not the repository

`test_runtime_artifacts_take_precedence_only_when_complete` failed on the host
with `KeyError: 'source'` while passing on every clean checkout.

`campaign_strategy()` reaches one production file by two routes: the
`pipeline_artifact_path` fallback, and `restored_artifact_path`, which derives
its directory from `pipeline_output_directory()`. The test redirected only the
first. A clean checkout has no runtime directory, so the unpatched route found
nothing and the fallback answered — the test passed for a reason that had
nothing to do with what it patched. On the deployment host that directory
holds real artifacts from an earlier run, and a complete runtime set
legitimately takes precedence over the baseline, so the unpatched route
returned the host's own strategy file and the fixture was never read.

The fix redirects both routes, and the whole class now runs against a temporary
empty directory. That closed a second latent failure at the same time: a host
carrying a complete attribution set would have failed the dashboard contract
test on row counts, and no clean checkout could have revealed it.

### Broad exclusions kept a deleted tree alive

The synchronization step reported seven `cannot delete non-empty directory`
lines under
`external/campaign-optimizer-llm-integration/MTA-strategy-optimizer/`.

That path is a recursive submodule checkout the published snapshot no longer
carries, so `--delete` should have removed it. It survived because rsync
protects an excluded file from deletion and therefore refuses to remove any
directory containing one. The rules were written unanchored, so `__pycache__`
matched at every depth; one cache directory inside the stale tree pinned every
parent above it. The names read as "preserve host state", but an unanchored
name is not a location — it is a pattern that also matched deep inside trees
that were supposed to disappear.

Each rule is now anchored with a leading slash to the single place that state
actually occupies. Regenerable state is deliberately no longer protected: the
later steps rebuild it, and a compiled module surviving beside the source file
it came from is a correctness hazard, not preserved state.

## Verification

- Reproduced the host failure locally by planting the leftover artifacts,
  confirmed the exact `KeyError: 'source'`, then confirmed the fix. A control
  run against the unfixed suite reproduced both that error and the latent
  attribution-count failure, so neither test passes vacuously.
- Ran the six suites the deployment runs — 768 tests — on a clean tree and
  again against a host carrying a full set of leftover artifacts. All pass in
  both states; previously the second state failed.
- Reproduced the seven synchronization messages against a tree matching the
  deployment log, then confirmed the anchored rules remove the stale checkout,
  preserve `.env`, the virtualenv, both dependency trees, the built client and
  `generated/`, and repeat cleanly on a second run.
- Confirmed the new guard is not vacuous: it fails the run under the previous
  rules and passes under the current ones.

## Limits

`--delete` no longer preserves Python caches, so the first deployment after
this change removes the host's existing ones and the interpreter rewrites them.
The synchronization step is verified against a reconstruction of the host tree,
not against the deployment machine itself; the messages it reported are the
ones reproduced here, but only a real run confirms the live tree is clean.
