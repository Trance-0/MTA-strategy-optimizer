# Version 0.9.56

Date: 2026-09-10

## Changes

- Added a **Local preview before deployment** section to `AGENTS.md`: a change
  that alters a major component or adds a feature must ask the owner whether to
  bring up a local Docker Compose stack for preview first.
- Added [Repository Rules Index](/en/introduction/repository-rules) under
  `docs/en/introduction/` — one sentence per rule, numbered continuously, each
  carrying the date it was introduced and who introduced it. Linked it from the
  project overview's reading order and topic entry points.

## The preview rule

The automated suites run with `DATABASE=false`, so they exercise the file-mode
path and never the database path a deployed instance actually uses. Six suites
passing is therefore not evidence that a deployed instance works, and the
deployment step is the first place that difference becomes visible — which is
too late, because it is also the step that changes what users see.

The rule closes that gap with a person rather than another automated gate. The
agent asks; the owner decides. It must not start a stack unsupervised, and it
must not skip asking because the tests passed, which is exactly the reasoning
the rule exists to interrupt.

The preview runs through the stack already in `deploy/docker/`, not a new one,
which keeps it under the existing file-count rules. That stack ships
`DATABASE=false` with empty `PG_*` fields, so exercising the database means
supplying real credentials — and those come from the git-ignored root `.env`,
never from a tracked file. The rule states this explicitly because the tracked
`defaults.env` is the obvious wrong place to put them.

## The rule index

`AGENTS.md` had grown to eighteen sections of dense prose. Every rule was still
there, but the set could not be reviewed as a set: an owner checking whether a
rule existed, or what it required, had to read the whole file.

The index gives each rule one numbered sentence, its introduction date, and its
author, so the whole body of instructions can be audited in one pass. Numbers
are continuous across the page, so a rule can be cited as "rule 63" in review
without naming its section.

It is published as a documentation page rather than appended to `AGENTS.md`
because the two files serve different readers. `AGENTS.md` is written for an
agent that loads the whole file before acting, and doubling its length to serve
a human reader would make it worse at the job it exists for. A person reviewing
the rule set has less context to spend than the agent does and needs the short
form. So the prose and the summary live apart: `AGENTS.md` keeps the binding
wording, and an index line is a pointer, never a replacement. The page says so,
and where the two disagree the summary is the defect.

Dates and attribution are read from `git log` on the file rather than
reconstructed. Every rule to date traces to one person, recorded under three
author names — `Zheyuan Wu`, `Trance-0`, and one `Trnace-0` typo.

## Verification

- Confirmed by script that both files carry the same eighteen sections in the
  same order, that each section's rule count matches its bullet count, and that
  the numbering runs 1 to 107 with no gap or repetition. One bullet under
  Script placement carries two separate obligations and is deliberately listed
  as two lines; the index preamble records that exception.
- `AGENTS.md` is 163 lines, well within the 500-line ceiling for root markdown.
- The English documentation build passes and the new page's inbound links from
  the project overview resolve.

## Limits

The dates are commit dates for the change that introduced each rule's wording.
Where a rule was later reworded in place, the date still reflects its
introduction, which is the useful fact for review but not a full edit history.

Nothing enforces that the index stays in step with `AGENTS.md`; rule 90 states
the obligation, and the verification above is a script that was run by hand, not
a build gate.
