# Version 0.9.7

Date: 2026-08-14

## Changes

### Published dashboard

- Deployed the dashboard to GitHub Pages at the site root, with the documentation moved one level down to `/docs/`. Both are built into one artifact by `.github/workflows/deploy-pages.yml`.
- GitHub Pages serves static files and cannot run a Streamlit server, so the published copy runs the same `dashboard/` Python in the visitor's browser through stlite, which executes Streamlit on Pyodide. `script/build_pages_site.mjs` copies the sources rather than forking them, and fails the build when `web/index.html` and its own file list disagree — a mismatch would otherwise surface as a missing-module error in a visitor's console instead of in CI.
- Established that the browser build cannot read the database and says so. WebAssembly has no raw TCP socket, so no configuration could reach PostgreSQL from that page. `web/index.html` exports `DASHBOARD_HOSTED`, `config.use_database()` returns false whenever it is set, and the settings modal replaces the credential form with the local-run instructions rather than offering fields that could never connect.
- Published only the eleven artifacts the file-mode loaders actually read, about 330 KB. The 2.8 MB synthetic-events extract is excluded because no view reads it. Source maps are excluded from the stlite runtime: at roughly 58 MB they were two thirds of the site.
- Built the documentation with its base path set to the Pages base plus `docs/`, because Pages performs no rewrites and VitePress resolves every internal link and asset URL at build time. The two are joined rather than concatenated, since `base_path` carries no guarantee about a trailing slash.

### Links and start scripts

- Added **Docs** and **Repo** to the foot of the rail. A reader who arrives at the published dashboard has no other route to the specification or the source, so the app carries them; the documentation link is relative in the published build and absolute in a local run.
- Added `dashboard/run.sh` and `dashboard/run.bat`. Both resolve the repository root themselves, verify `uv` is installed, copy `sample.env` to `.env` when none exists so a fresh clone starts in file mode, skip `uv sync` when the extra is already present, and take an optional port.

### Corrections

- Updated the submodule `external/campaign-optimizer-llm-integration` to its current `main`.
- Fixed the rail foot, where the outbound links changed the height budget and left the gear icon overlapping the logging pill. The gap now hangs on the first element container rather than on every markdown block in the foot.

## Verification

- `uv run --extra dashboard python -X utf8 -B -m unittest discover -s dashboard/tests -p "test_*.py"` passes at 11 tests, including one asserting that `DASHBOARD_HOSTED` forces file mode even when `DATABASE=true` is set.
- `npm run build` in `docs/` with `DOCS_BASE_PATH=/MTA-strategy-optimizer/docs/`, then `node script/build_pages_site.mjs`, assembles a 64 MB site.
- The assembled site was served locally and opened in a real browser under the deployed path prefix. The app booted in 80 seconds on a cold cache with no exception, rendering nine rail buttons, five metric tiles, and four Plotly traces on a light surface; the status read "Sample data" and both outbound links resolved to the sibling documentation and the repository.
