# Version 0.9.31

Date: 2026-08-27

## Changes

- Selected which schema of the PostgreSQL instance the dashboard reads. One instance now holds several — this project's tables in `public`, three research scenarios behind `mta` — and the connection resolved every table through whatever `search_path` the server happened to hand out, which in practice meant `public` always. A schema was therefore something a reader could see in their database client and not reach from the page. `PG_SCHEMA` names it, and the settings dialog offers a dropdown over what the connected server actually holds.

- Applied the selection to the connection rather than to each statement. The dashboard builds statements two ways: from `dashboard/models.py`, which names no schema, and as reflective reads of the external `mta_sim_*` tables, which name none either. Qualifying either would have meant a second definition of where a table lives, and SQLAlchemy's `schema_translate_map` covers only the first. One libpq `-csearch_path=` connect option in `DatabaseSettings.connect_args()` makes both follow the selection, and `table_exists()` stopped hardcoding `public.` so that a probe and the read after it can no longer disagree about which schema they are asking about.

- Made the selected schema the whole search path, with nothing behind it. The forgiving choice was written first and reverted: `-csearch_path=mta,public` would let a schema holding research history but not this project's tables resolve the rest from `public`, and put one scenario's attribution beside another's history with nothing on the page saying so. Missing must read as missing. `pg_catalog` is searched implicitly and holds every function these statements call, so pinning costs a read nothing.

- Added `backend/services/schemas.py`, which reports a capability rather than a name. It enumerates every readable schema in one round trip over `pg_namespace` and `pg_class`, filtered by `has_schema_privilege(current_user, ..., 'USAGE')` so the list can never advertise a schema whose selection would fail, and marks a schema selectable only when it holds all fourteen tables the dashboard's loaders read directly.

- Listed the schemas that cannot serve the dashboard rather than hiding them, disabled. Omitting `mta` would leave a reader who knows it exists with no account of its absence; the disabled option puts the reason at the moment they would have chosen it. Each carries the server's own explanation — how many tables it holds, which of the required ones it lacks, and the command that would populate it — as both the option's tooltip and help text under the field, because the browser tooltip is not shown over an open dropdown everywhere and a hover may never arrive.

- Offered the right remedy per schema rather than one command for all of them. A schema already holding another account's history is told to derive; only an empty one is told to run the fixture importer, which carries its own advertiser and Campaigns and would otherwise staple them onto observations belonging to someone else. The first draft named the importer in every case, which for `mta` was an instruction to corrupt it.

- Reported each schema's real relation count instead of the matched subset. The census matches only the tables selectability turns on, so `public` was described as holding 18 tables when it holds 53 — a reader comparing that against their database client would reasonably conclude the connection was pointing somewhere else. The statement now returns both numbers, because they answer different questions.

- Filled the dropdown from a connection test as well as from the saved state. A test is the only moment the list is knowable for credentials that have not been written yet, so the reader edits the host, tests, and the list becomes that server's. The census is held apart from the rest of the settings state for that reason. The stored selection stays in the list even when the census is empty, so an unreachable database cannot make the dialog show a schema the reader never chose and then save it on the next write.

- Named the schema in the unavailable-database message, and separated a schema that lacks `attribution_result` from one whose `attribution_result` is empty. The two need different fixes, and a reader who has just selected a research-only schema is the most likely person to meet the first. The message names both remedies: choose a schema that carries the dashboard tables, or run the import command against this one.

- Gave `script/import_to_database.py` a `--schema` flag, so the reader and the writer resolve their target from the same `PG_SCHEMA` and an import cannot land somewhere the dashboard is not looking. A named schema is created before any table is, because a `search_path` pointing at a missing schema reports every table as absent rather than saying the schema is not there. `--replace` drops and rebuilds within the selected schema alone, and the `Target:` line printed before any write names it.

- Validated the schema name as an identifier at three points, because a schema names an object and cannot be a bound parameter. `valid_schema_name()` accepts only an unquoted PostgreSQL identifier; `POST /api/settings` returns `400 invalid_schema` before `.env` is read or written, `test_connection()` refuses before opening a socket, and `connect_args()` raises rather than building an option that could close and open another. A schema whose name is not a plain identifier is dropped from the census rather than offered and later refused.

- Added `PG_SCHEMA` to `sample.env`, `deploy/docker/defaults.env`, and the AppStack ConfigMap through a new `pgSchema` value. That deployment sets `DASHBOARD_CONFIG_READ_ONLY=true`, so its schema is chosen in the AppStack environment and takes effect on restart rather than from the browser.

- Added `script/derive_scenario_schemas.py`, which makes a simulator-populated schema readable instead of merely explaining why it is not. The `mta` schema holds three scenarios' worth of real data — 7,665 path rows, 13,140 delivery observations, a full year each for ASIA, EUROPE, and US — and none of the tables `dashboard/models.py` defines. The importer could not be pointed at it: it writes the committed sample's advertiser and Campaigns, which would have attached the demo account's entities to another account's observations. The command derives the model from the scenario's own rows instead.

- Derived one schema per scenario rather than one filtered view of a shared one. The dashboard model holds one advertiser, one marketplace, and one report window, and reads `attribution_run` as a single row; the simulator writes three marketplaces into one schema. Splitting on the way out keeps that contract intact and makes the schema dropdown the scenario picker, rather than teaching every loader a filter it would then have to apply consistently.

- Summed each path's 365 daily windows into the one window the comparison requires, rather than sampling a day. `compare_attribution_models()` refuses a report carrying more than one window, and picking a representative day would have discarded 364 of every 365 rows. The row-level invariants survive the sum because they hold termwise, and each row is stamped with the scenario's own window rather than the dates that path happened to appear on — per-path extremes would produce as many windows as there are paths and fail the same check the aggregation exists to satisfy.

- Reused the published attribution code rather than restating it. `run_markov_attribution`, `run_shapley_attribution`, `aggregate_spend_by_touchpoint`, and `compare_attribution_models` are imported from the modules that own them, so a derived schema and a published artifact are two renderings of one calculation and cannot drift into disagreeing.

- Restored the two columns the Ads report has and the simulator's table does not. `interaction_type` is read back off the fifth segment of the key the simulator already wrote rather than guessed, which lets `touchpoint_key_from_ads_row()` rebuild the key from the other columns and verify it against that stored value — the check that catches a key and its columns disagreeing. It passed on all 4,380 US rows. `cost_type` follows from the interaction by the project's own CPC/CLICK, CPM/IMPRESSION pairing.

- Split the touchpoint-to-entity bridge, the one derived quantity with no direct source. The simulator records delivery per Campaign and per touchpoint; attribution produces an outcome per touchpoint across all Campaigns. Where a touchpoint was delivered by a single Campaign the whole outcome belongs to it and nothing is assumed; where several share one, the outcome divides by each Campaign's share of that touchpoint's cost, because cost is the quantity the strategy module reallocates and delivery volume alone would credit a cheap high-impression Campaign over an expensive converting one. Each share then divides across Products by the revenue the simulator recorded per Campaign, touchpoint, and Product. Total cost reconciles to the Ads report exactly.

- Wrote a count the simulator does not establish as zero rather than as a plausible number. It models delivery, not the targeting objects a new Ad Group would be built from, so only the SKU count can be sourced honestly. A fabricated keyword or audience count would have flowed straight into a recommended Ad Group count and a daily budget, which is a confident number about a Campaign Group that was never run.

- Reported every reason a budget recommendation is impossible rather than the first. The simulator's six Campaigns span four ad products with two appearing twice, and the strategy module reaches a Campaign only through its ad product; separately, `recommend_ad_group_count()` requires positive keyword and legal-pair counts for search products and positive target and audience counts for display. Fixing the Campaign shape alone would not have made a recommendation possible, so `budget_blockers()` checks both before calling rather than after failing, and the message names the property of the scenario rather than the contract clause it tripped.

- Copied each scenario's `mta_sim_*` tables into its derived schema, sliced by `run_id`. The Research view reads them reflectively through `search_path`, because the external simulator repository owns their schema and redeclaring it here would create a second definition free to disagree with the one that writes them. Without the copy a derived schema showed no runs, no budget response curves, and no per-currency Product economics, though the source held all three. A scenario is exactly one run, so the copy is an exact slice rather than a filtered approximation.

## Verification

- Fifty-four backend tests pass, twenty-two of them new. `backend/tests/test_schemas.py` covers the identifier rule in both directions — including the names that would close the connect option and begin another — that a selection produces `-csearch_path=<schema>` with no fallback appended, that `public` sets no option at all, that a complete schema is selectable and a research-only one is not, that the missing-table list is capped at eight while the count still states the true size, that the count reported is the whole schema and not the matched subset, that a schema already holding history is never told to run the fixture importer while an empty one is, and that selectable schemas sort ahead of the rest. `backend/tests/test_settings.py` adds the `400 invalid_schema` refusal and asserts `PG_SCHEMA` is in `ENV_KEYS`, without which the dropdown would appear to save and forget its selection on the next start.

- Twenty-nine dashboard tests pass, two of them new: that the dropdown renders `:disabled="!option.selectable"` with the server's `detail` as both `title` and `aria-describedby` help text, that the saved selection survives an empty census, and that `PG_SCHEMA` is sent, refused as `invalid_schema`, and refilled from a test result. The existing rule that no interface string presents the data as generated or simulated still passes, which is why the derivation command is named for what it produces rather than what it reads.

- Verified against the live instance. The census returns `public` selectable with 53 tables, the three derived schemas selectable with 29 each, and `mta` unselectable with 14 tables and 14 missing, its detail naming the derivation rather than the importer. `PG_SCHEMA=mta -c log_statement=all` was refused with no connection opened.

- Derived all three scenarios and built the real snapshot against each. Every one returns all fifteen keys with 4,380 Ads rows, 24 attribution results, 36 comparison touchpoints, 36 recommended rows, 12 touchpoints, 18 bridge rows, and 20 to 23 aggregated paths; the Research view carries 1 run, 3 Products, 9 Product economics rows, 3,285 history rows, and 4,380 delivery rows. Recommended shares sum to exactly 1.0 per outcome, and bridge cost reconciles to the Ads report to the cent.

- The settings response carries no password: the full `settings_state()` payload was serialized and checked for the key, in addition to the existing rule that a stored password is never echoed.

## Known Gaps

- **The Budget Manager's recommendation section is empty in all three derived schemas**, and no rearrangement of the derivation would fill it honestly. The strategy module models a Campaign Group of exactly four Campaigns, one per Amazon ad product, because it reaches a Campaign only through the ad product a touchpoint names; the simulator runs six across four, with `SPONSORED_DISPLAY` and `AMAZON_DSP` each appearing twice. Folding six into four would not be enough on its own: sizing a Campaign also requires positive keyword and legal-pair counts for search products and positive target and audience counts for display, and the simulator models none of those. Every other view is complete. Filling this needs the simulator to model targeting inventory, or a decision to accept fabricated counts — which would make the recommendation a statement about a Campaign Group that was never run.

- Ad Group keyword, target, and audience counts render as zero in the derived schemas' Budget Manager, for the same reason: `master_data.py` counts them from bridge fields the derivation leaves absent rather than invented. Products, Product Economics, and Campaign-Product Links fill, because `sku_id` is sourced from the scenario's own links.

- The derivation has no test file of its own. It is verified by running it against the live instance and reading the result, which proves the current data rather than the contract. The attribution and comparison code it calls is covered by the modules that own it; the derivation-specific logic — the window aggregation, the cost-weighted bridge split, the blocker report — is not.

- The selection is deployment-scoped rather than per-viewer. One process holds one engine pinned to one schema, so two readers of the same server see the same schema, and changing it is a settings write that disposes the pool. A per-request `?schema=` parameter would also poison the ten-minute snapshot cache, which is keyed by loader name alone.

- The census discloses the schema names of the connected database to anyone who can reach the settings page. This is the same class of disclosure the existing connection test already makes, and the application has no user authentication by design — a deployment places TLS and basic auth in front of it, as `setups.md` requires.

- `docs/version/` now carries seven flat patch pages against the four the file-management rule keeps outside a minor-version folder. Moving the oldest into `0.9/` remains a documentation-structure change with its own cross-reference edits, deliberately not bundled here.
