# Version 0.9.53

Date: 2026-09-09

## Changes

- Wrapped the mirror's `git push --atomic --force --prune` and its `git ls-remote`
  verification in a bounded retry that reacts only to a transport fault: a 429 or
  5xx from the gateway, an unresolvable host, a reset or timed-out connection, an
  empty reply, or an unexpected disconnect.
- Limited the retry to five attempts with a growing pause between them, and left
  every answer that Gitea itself produces — a rejected reference, a declined hook,
  a non-fast-forward, a failed authentication — failing immediately as before.
- Recorded the reason inline as a comment beside the retry, including why
  retrying is safe for an atomic push.

## The defect

With the 0.9.52 attribute fix in place, the workflow prepared a valid snapshot
and reached publication for the first time. It then failed at the push:

```
fatal: unable to access '***/': The requested URL returned error: 502
```

and the job ended with exit code 128. The trailing slash in that message is
git's *reference discovery* request, which is the first contact with the remote
and carries no object data. So the failure happened before a single byte of the
pack was offered, which rules out repository size, pack limits and push
permission as the cause.

`git.trance-0.com` answers through an `openresty` reverse proxy. When that proxy
cannot reach Gitea it returns its own 502, and git reports the gateway's status
rather than an answer from Gitea. Probing the live host's
`info/refs?service=git-receive-pack` endpoint directly returned 502 on 2 of 6
requests in one burst and 401 — the normal authentication challenge for a
private repository, meaning the request did reach Gitea — on the other 4. The
fault is intermittent and external to this repository, so a single attempt makes
the whole mirror a coin flip.

## Verification

- Seventeen behavior checks against the shipped function: a 502 that clears on
  the third attempt succeeds and forwards its output unchanged; 503 and 429
  retry; a remote rejection, a declined pre-receive hook, a non-fast-forward and
  an authentication failure each fail on the first attempt without retrying;
  a persistent fault stops at five attempts; and `ls-remote` output survives the
  wrapper intact, since the verification `diff` consumes it.
- End-to-end against disposable local repositories with a git wrapper that fails
  the first two pushes exactly as the proxy does: the transaction recovered on
  the third attempt and the published branch and tag set matched the prepared
  references.
- Confirmed the live host resolves and accepts connections on port 443, and that
  the 502 is not a cold-start effect: after four minutes idle, six consecutive
  probes all returned the normal 401.
- The workflow file parses as YAML and its publication step passes `bash -n`.

## Limits

The retry makes an intermittent gateway fault survivable; it does not repair the
proxy. A gateway that is down for longer than five attempts still fails the job,
which is the correct outcome — the mirror reports a failure rather than
publishing a partial one. Because the push remains `--atomic`, each attempt
applies every reference or none, so a retry always resumes from the previous
state and cannot merge two partial publications. Only a live Action run proves
authentication and force-update permission against the real host.
