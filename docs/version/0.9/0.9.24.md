# Version 0.9.24

Date: 2026-08-20

## Changes

- Consolidated the Linux deployment's three separate system paths (`/etc/mta-dashboard`, `/opt/mta-dashboard`, `/var/lib/mta-dashboard`) into one `${DEPLOY_DIR}/installation/{config,app,state,systemd}` tree owned by the uploaded bundle itself, so the transfer bundle for a new deployment is now just `run.sh` and `.env` side by side. `enqueue_deploy.sh` and `deploy_worker.sh` are embedded inside `run.sh` as base64 payloads that `install_or_update` and `--check` decode, verify against `ENQUEUE_RUNTIME_SHA256`/`WORKER_RUNTIME_SHA256`, and syntax-check with `bash -n` before ever writing them to disk, rather than requiring the whole `deploy/runtime/` directory to be uploaded alongside `run.sh`.
- Since the `mta-dashboard` service account no longer owns `$DEPLOY_DIR` (an arbitrary upload path outside its home directory), `grant_service_traversal` walks up from `$DEPLOY_DIR` granting execute-only ACL entries (`u:mta-dashboard:--x`) at each ancestor and records exactly which paths it touched in `.installer_acl_paths`, so uninstall removes only what it granted rather than guessing. `terminate_stale_project_processes` and both uninstall paths recognize the previous fixed paths as `LEGACY_ETC_ROOT`/`LEGACY_INSTALL_ROOT`/`LEGACY_STATE_ROOT`, migrating them and then deleting them once the new-path release is confirmed healthy, so an existing production host's prior installation is not left orphaned by the path change.
- Added a `deploy_progress` state file — `write_progress` in `deploy_worker.sh` writes phase, percentage bounds, a start timestamp, a typical duration, an ETA, and a message at each phase transition — and had `run.sh` read it during `wait_for_initial_deployment`, service removal, and both uninstall paths to render a live phase name, an interpolated percentage, elapsed time, and an ETA, replacing the previous unlabelled wait with visible progress and a pointer to `journalctl -u mta-dashboard-deploy.service -f` for the underlying Git and npm output.
- Bounded every destructive deletion to its approved root: `remove_tree_with_progress` enumerates a target with `find -P -xdev`, refuses any manifest entry that resolves outside the target directory, and deletes leaf-first with `rm -f`/`rmdir` rather than a recursive `rm -rf`, so a symlink or a mid-run race cannot walk a deletion outside the intended tree. Full uninstall now also removes the recorded traversal ACLs and reports the same bounded progress as installation.
- This restructuring was authored in an earlier, uncommitted working session. While reviewing it before commit, found that the base64 payload embedded in `run.sh` for `deploy_worker.sh` was a byte snapshot still carrying the pre-[0.9.23](0.9.23.md) `dashboard_healthy()`, which gated activation on `GET /api/dashboard` — the exact bug fixed in 0.9.23. Because the embedding is a point-in-time copy rather than a live reference to `deploy/runtime/deploy_worker.sh`, `verify_embedded_runtime`'s checksum check would have passed while silently redeploying the pre-fix worker on every install using the new single-file transfer path. Regenerated the payload and `WORKER_RUNTIME_SHA256` against the current file and confirmed a byte-for-byte match after decoding.

## Verification

- `bash -n` on `run.sh`, `deploy_worker.sh`, and `enqueue_deploy.sh`.
- Decoded both scripts embedded in `run.sh` and diffed them byte-for-byte against `deploy/runtime/enqueue_deploy.sh` and `deploy/runtime/deploy_worker.sh`; recomputed and matched `ENQUEUE_RUNTIME_SHA256`/`WORKER_RUNTIME_SHA256` against the current files.
- Read the full diff for credential-bearing strings; found only the pre-existing `GITEA_TOKEN`/`PG_PASSWORD` configuration key names, never a value, consistent with `.gitignore` already excluding `deploy/.env`.
- No Linux host was available to exercise `run.sh` end to end (install, uninstall, or the ACL grant path); verification here is static (syntax, checksum, and diff review), not a live install.

## Notes

- The install/uninstall progress bars read a file `deploy_worker.sh` writes and `run.sh` polls; if a future change adds a phase to one without the other, the bar will simply not move for that phase rather than error, since `render_progress_bar` clamps to the last known percentage.
