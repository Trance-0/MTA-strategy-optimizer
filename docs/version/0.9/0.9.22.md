# Version 0.9.22

Date: 2026-08-19

## Changes

- Added `dashboard/src/lib/deployment.js` as the single place the dashboard asks which deployment it is. Write capability is derived from the snapshot's own `mode`, **not** from `VITE_STATIC_BUILD`: a local run reading the committed files is read-only for exactly the same reason the published build is, and deriving the answer from the build flag would have offered editing controls to that local run. The build flag now decides only how a read-only deployment names itself and which remedy it offers, since a reader can act on a local run but not on a published one.
- Themed the two deployments apart. `theme.js` gained `DEPLOYMENT_THEMES`: Microsoft Excel's own green `#217346` wherever the dashboard reads committed files and cannot write, and the reference prototype's brand blue where PostgreSQL is connected. `App.vue` applies the selected set by overriding the custom properties `style.css` already reads, so one override repaints the rail, tabs, primary buttons, and selection highlight and no component needs a variant class. The chart series palette is deliberately excluded, because a series colour follows its entity and the same Campaign must not change colour between the two sites; a test asserts the two sets never intersect.
- Stated read-only status rather than only enforcing it. Every view now carries a notice naming why data operations are unavailable and the remedy that applies, the header leads its tag row with the deployment, and the rail's status dot was aligned to the read-only accent in both the server's `status()` and the static build's client-side equivalent, so the rail and the theme cannot disagree about which deployment this is.
- Replaced Budget Manager's seven `<details>` detail lists with `EntityTable.vue`, a 1Panel-style resource list. A row is now an abstract of declared summary columns and the whole record sits behind that row's Edit control, in place of a layout that rendered every field of every record as stacked paragraphs — hundreds of lines of prose on one page, with no way to scan a column or compare two records. The component owns paging, page size, filtering, and selection; the view still declares the columns, so a new snapshot field cannot silently widen a table.
- Added paging at 15 rows by default with 15, 30, 50, and 100 offered, a free-text filter across the rendered text of the declared columns, and batch selection keyed by a caller-supplied row identity rather than by page index — keyed by index, a batch action would have acted on whatever record occupied that index after the page turned.
- Added `ConfirmDialog.vue` as the only route to a deletion, for both the new per-row Delete control and the batch action. It names the affected identifiers rather than reporting a count alone, caps the list at twelve with the remainder stated, and stays open on failure. A batch archives sequentially, because each archive clears the server's caches and a parallel batch would have them racing; a failure stops the run and reports which identifier it stopped at, rather than reporting success after a partial batch.
- Extracted `renderCell()` and `NUMERIC_FORMATS` into `src/lib/common.js` so `DataTable` and `EntityTable` share one cell renderer and a column declaration cannot mean two things in two tables. The shared renderer additionally flattens an array to a comma-joined list and an object to JSON, which the canonical entity records need: `String(value)` renders a Provider's supported ad products correctly only by accident and a Product's provider identifiers as `[object Object]`.
- Made an empty entity section name its cause. These records come from a generated Multi-Touch Attribution Simulator (MTA-SIM) run that the committed sample artifacts do not carry, so the published build shows every section empty — the expected state, which "No records loaded" alone reads as a fault. Each empty section now names `MTA_SIM_DATA_DIR` or `script/import_to_database.py` as the remedy.

## Verification

- Passed 47 dashboard tests, 13 of them new: capability follows the snapshot mode rather than the build flag, the two accents differ and neither leaks into the chart palette, both read-only deployments name a remedy, the rail dot matches the read-only accent, the page sizes and default, identity-keyed selection and the reassigned Set, confirmation before every deletion, the partial-batch report, the absence of any remaining `<details>` list, the empty-state cause, the single shared cell renderer, `renderCell()`'s array/object/null handling, and the styled destructive control.
- Confirmed the reported layout difference is data emptiness rather than a design divergence, by probing both running deployments. File mode returns `providers=0, products=0, campaigns=0, adGroups=0, touchpoints=0`; the same build against the configured PostgreSQL instance returns `providers=1, products=1, campaigns=40, adGroups=40, touchpoints=7, econ=2, configs=1, drafts=1`. `script/export_dashboard_snapshot.mjs` pins `DATABASE=false` and the Pages workflow sets no `MTA_SIM_DATA_DIR`, so the published snapshot carries the empty arrays by construction.
- Built both targets successfully — `npm run build` and `npm run build:static` — and probed the served bundle and stylesheet over HTTP for every new string and rule: the read-only notice, all three deployment labels, the pager, the batch and confirm controls, the empty-state remedy, the Excel green, and the `.btn.danger`, `.entity-toolbar`, `.entity-pager`, `.confirm-modal`, and `--blue-strong` rules.
- Confirmed the server enforces the same rule the client renders: `DELETE /api/master/product/p1` against a file-mode server answers `403`, and the rail reports `Local files` with the read-only dot `#7ed6a4`.

## Notes

- The three deployments remain one source tree and one snapshot contract. No view branches on the build flag; the only question a view asks is `useDeployment().writable`, which the server answers.
- The published build showing empty entity sections is unchanged behavior, now explained on screen rather than left to read as a defect. Publishing a populated snapshot would require exporting from a database, which `export_dashboard_snapshot.mjs` refuses by design so a private deployment's data cannot be baked into a public artifact.
