# Version 0.9.27

Date: 2026-08-20

## Changes

- Added `dashboard/server/jobs.js` and the `/api/jobs` routes, which run a pipeline stage from the dashboard by spawning the project's own documented command. A run started here and a run started in a terminal execute the same script with the same arguments, so the dashboard cannot drift from the pipeline it reports on, and the command is shown verbatim in the panel so a reader can reproduce it. The job outlives the request that started it and the client polls for progress, so a dropped connection during a long fit does not abandon the run.
- Made the progress bar report the stage the script is actually in rather than a timer. `run_pipeline()` and `run_attribution_models()` gained an opt-in `progress` callback, defaulted to `None` so an importing caller sees no output it did not ask for, and the command-line entry points pass a flushing printer. The server matches those lines to advance the bar monotonically: a later line naming an earlier stage never walks it backwards. A test asserts every declared phase pattern matches a line the scripts actually print, so a phase cannot silently stop matching and leave the bar stuck.
- Gave `script/run_pipeline.py` a working `--report-start-date` and `--report-end-date`. The window narrows **both** inputs into a temporary workspace — the Ads report by `reportDate` and the touchpoint events by `event_time` — because filtering the Ads report alone leaves conversions outside the window it implies, which is a validation failure. The narrowed copies live in the temporary workspace, so a windowed run never rewrites the committed reports it read from.
- Reconciled the two inputs under a narrowed window. The alignment validator requires the Ads report and the assembled paths to describe exactly the same touchpoint set; over the full window they do, but inside a narrower one a touchpoint can take delivery every day while the journeys that touch it convert outside the window. Measured against the committed reports, every window under about three weeks has at least one. Unmatched delivery is a property of the chosen window rather than a fault in the data, so those Ads rows are dropped and the excluded touchpoints are printed by name; dropping delivery rather than inventing events narrows what the run claims to cover instead of attributing outcomes to a touchpoint that recorded none. Reconciliation runs only under a narrowed window, so an unnarrowed run still fails on a genuine extract mismatch as it should.
- Split Campaign Optimizer into one tab per model — MTA attribution, MTA strategy optimization, MTA strategy evaluation — each with its own runner, and gave Optimization Log the same three tabs beside the provenance it already carried. The optimization tab surfaces the allocation, its evidence, and its extrapolation and pooled-transfer warnings. The evaluation stage is declared with `script: null` and an explicit reason: `modules/mta_strategy_evaluation/` and `script/evaluate_strategies.py` are specified but not built, and a named unbuilt stage reads as the roadmap it is where a missing tab would read as a dashboard defect.
- Validated every run option before it can reach a command line. Dates must be plain ISO dates, a total budget must be a positive number, and the budget usage policy must be one the `BudgetUsagePolicy` enum declares; the arguments are passed as a vector with `shell: false` rather than a string a shell would re-parse. A test pins the offered policies against `modules/mta_common/src/enums.py`, which caught the view offering `ALLOW_UNDERSPEND` — a value the enum does not declare, which would have failed the run only after it had already started.
- Converted Campaigns to the paged, searchable `EntityTable` that Budget Manager uses, replacing its bespoke `TableView`, `DataTable`, and separate path-search field, and gave each list a row key composed from the fields that distinguish a record. Fixed a pre-existing tab bug found in the same pass: the tab chain opened a second `v-if` mid-way, so the trailing `v-else` rendered the Conversion Paths panel underneath the Budget history tab.
- Specified the five new source files — `server/jobs.js`, `server/master_data.js`, `src/lib/diagnostics.js`, `src/lib/useJobs.js`, and `StageRunner.vue` — in the `## Source Files` sections that own them, and corrected the `server/index.js` and `src/api/client.js` entries for the routes this version added. Writing the `master_data.js` entry surfaced a verification claim no test backed, so the test was written rather than the claim softened; `useJobs.js` has no test it can have without a browser and its entry states that instead of implying coverage.

## Verification

- 61 dashboard tests pass, eleven of them new, covering the three model tabs and four log tabs, the refusal paths for a read-only deployment and an unknown stage, the option validation including a shell-metacharacter date, the phase-to-script correspondence, the derived entity catalogue, and the Campaigns table conversion.
- 476 Python tests pass across the four module suites.
- Ran a narrowed attribution stage end to end through the job runner (`2026-01-05` to `2026-01-20`): exit 0, all five phase lines emitted and matched, and the one unmatched touchpoint named in the output.
- Confirmed backward compatibility byte-for-byte: an unfiltered `run_pipeline.py` reproduces the committed artifacts exactly, leaving `git status` clean under `modules/`.

## Notes

- Running a stage is refused wherever the deployment is read-only, and refused before anything is spawned so a refusal never leaves a half-started run behind. The published static build has no server at all; a file-mode server would write outputs it cannot read back.
- The strategy optimization stage additionally needs a research snapshot to fit against, because fitting a budget-to-revenue curve needs the same Campaign observed at several budget levels and a single reporting window carries one.
