# Version 0.9.32

Date: 2026-08-27

## Changes

- Separated the schema used to serve dashboard views from the schema an
  operator wants to prepare. The existing **Dashboard schema** selector remains
  strict: it enables only schemas holding all required dashboard tables. The
  new **Schema setup** selector lists every readable schema from the same
  privilege-filtered census, including `public`, `mta`, empty schemas, partial
  sources, unrelated application schemas, and any future schema the connected
  role may use.

- Expanded each census result with `kind`, `canInitialize`, `canDerive`, and
  `sourceMissingCount`. A parse action is offered only when every table in the
  source contract is present; a partially uploaded dataset remains visible but
  cannot start a command already known to fail. Empty schemas can receive the
  committed sample, while populated non-dashboard schemas are never offered an
  initializer that would mix accounts.

- Added `GET`, `POST`, and `DELETE /api/schema-operations`. Initialization runs
  the maintained `script/import_to_database.py --schema <target>` command;
  parsing runs `script/derive_scenario_schemas.py --source <source> --all` and
  leaves the source read-only while producing one dashboard schema per
  scenario. Both use fixed subprocess argument vectors, saved database
  settings, and a fresh capability census immediately before spawning.

- Required `DATABASE=true` on a writable local deployment and a saved,
  unchanged connection before the browser can start setup. A complete
  dashboard schema can be rebuilt only when replacement is explicitly enabled;
  replacing existing derived targets requires the same explicit choice. The
  browser then names the affected schema and asks for confirmation before the
  destructive flag reaches the backend.

- Added a polled operation record containing the reproducible command, source
  or target schema, lifecycle state, start and finish timestamps, exit status,
  error, and combined process output. Each output line is timestamped and
  capped at 500 characters; the operation retains the newest 600 lines and
  reports how many earlier lines were dropped. Closing settings does not stop a
  run, while the explicit stop control requests process termination.

- Disposed the database connection pool and cleared snapshot caches after a
  successful operation, then refreshed the schema census so new targets appear
  in the active selector without a server restart. Connection or census
  failures become bounded refusal objects rather than unhandled server errors.

- Updated the database-import, backend-operation, backend-setup, dashboard
  boundary, and view specifications before changing their implementations.
  Moved versions `0.9.25` through `0.9.28` into the existing `0.9/` history
  folder so only the latest four patch pages remain flat in `docs/version/`.

## Verification

- Sixty-eight backend tests pass. New coverage proves fixed command arguments,
  explicit replacement, safe and unsafe schema classification, invalid-name
  and failed-census refusals, bounded timestamped logs, route registration,
  file-mode protection, and strict Boolean request handling.

- Thirty dashboard tests pass, including the discovery-driven setup menu,
  initialization and parsing controls, operation command and output rendering,
  and the existing rule that account-facing interface text does not describe
  reported data as generated or simulated.

- The Vue production build and VitePress documentation build complete. Ruff
  lint and formatting pass for every touched Python file, and Git reports no
  whitespace errors.

- A read-only probe of the configured database classified `public`,
  `mta_asia`, `mta_europe`, and `mta_us` as dashboard-ready and `mta` as a
  complete parse-ready source. No initialization, replacement, or parsing was
  executed during verification.

## Operational Notes

- Operation state and logs are held in the backend process memory. A process
  restart clears the displayed record but does not reverse database work that
  already committed.

- Setup commands always use saved connection settings rather than unsaved form
  values. Test and save the connection first, then start initialization or
  parsing.
