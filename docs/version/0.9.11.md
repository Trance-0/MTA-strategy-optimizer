# Version 0.9.11

Date: 2026-08-15

## Changes

### The dashboard is now a Vue client over a Node API

- Replaced the Streamlit presentation layer with a Vue 3 client (`dashboard/src/`) over an Express JSON API (`dashboard/server/`). One Node process serves both, so a local run remains one command and one port. The six views, the navigation rail, the settings dialog, and the `DATABASE=true/false` contract are unchanged in behavior.
- Replaced the stlite published build with a static Vue build. GitHub Pages cannot run the Express API, so `script/export_dashboard_snapshot.mjs` writes the same payload the API returns to `data/snapshot.json` at build time and the client fetches that file instead. It is the same client source, a different data path, never a different codebase — the browser-side counterpart of the dual-source contract.
- Removed `dashboard/app.py`, `settings.py`, `theme.py`, `data_source.py`, `views/`, `tests/test_views_render.py`, `web/index.html`, and `script/verify_source_parity.py`. `dashboard/config.py` and `dashboard/models.py` remain, because `script/import_to_database.py` needs them; the `dashboard` extra therefore drops Streamlit, Plotly, and pandas and keeps only SQLAlchemy, `psycopg`, and `python-dotenv`.
- Rewrote `dashboard/run.sh` and `dashboard/run.bat` for the Node stack. Both check the toolchain, the configuration, the dependencies, and the client build as four named steps, install and build only when what they produce is absent, and hide a successful install's output while keeping a failed one. A fresh clone gets a working page from one command; a warm checkout starts immediately.
- Repointed `.github/workflows/deploy-pages.yml` and `script/build_pages_site.mjs` at the static Vue build. The assembler now refuses to run when the build carries no snapshot, because without it every view would render its error card and reach a visitor as a broken page rather than as a failed build.

### Five defects the launchers found on a clean machine

Testing the launchers the way a new reader meets them — no `node_modules`, no build, no `.env`, and Node absent from `PATH` — found five failures that a warm checkout never reaches:

- **The version floor was a major number, and the real requirement is not.** Vite's engine range is `^20.19.0 || >=22.12.0`, and its bundler binding is an *optional* dependency carrying that same range: on Node 22.11 npm skips it silently, reports a successful install, and the build then fails with `Cannot find module './rolldown-binding.win32-x64-msvc.node'`, which names neither Node nor the version. Both launchers now compare `major * 1000000 + minor * 1000 + patch` against each boundary of that range and refuse before installing anything.
- **`npm --prefix` does not do what it reads as.** It sets where `node_modules` is written but not where the manifest is read from, so on the npm 10 that ships with Node 22 a cold start failed with ENOENT for a `package.json` at the repository root. Both launchers now run npm from `dashboard/`.
- **A port in use printed "Listening on …" first.** Express's `app.listen(port, callback)` also registers that callback as `server.once("error", …)`, so a callback written for a successful bind runs on failure too, with the error as a first argument an arrow function taking none silently drops. `listen()` is now called with no callback and both outcomes are handled as events.
- **An unrecognised argument exited 0.** In `run.bat` the rejection sat inside a `for` inside a parenthesised `if`, and `exit /b 2` there prints its message but returns 0 to the caller, so a typo in a script invoking this one looked like a successful start.
- **`--help` printed four lines in `run.bat` and the whole banner in `run.sh`.** Both now print the same banner, each read from the file itself so the help and the file cannot disagree.

Two smaller ones alongside: a failed server exit closed the window on an Explorer double-click before the diagnosis could be read, and both scripts reported "not a git checkout" when git was simply not installed, which sends a triager looking for a damaged clone.

### Three dual-source parity defects

The published contract is that no view can tell which source it is reading. Three defects broke it, all in `dashboard/server/data_source.js`:

- **Row order.** Five queries ordered by a business key — `campaign_id`, `revenue desc`, `ad_group_slot_id` — while the file loaders return each artifact's own order. The four demonstration Campaigns are written `SP, SB, SD, DSP` and sort alphabetically to `DSP, SB, SD, SP`, so the two deployments showed the same numbers against different rows. Every query now orders by the surrogate `id`, which the importer's insertion order makes equal to the artifact's order. Row order is now stated as part of the contract rather than left implicit.
- **Date formatting.** The four dates rebuilt from the strategy documents were formatted with `String(date).slice(0, 10)`. A `Date` stringifies to `Tue Mar 31 2026 …`, so the first ten characters are a weekday and a month name; the API returned `"Tue Mar 31"` in database mode and `"2026-03-31"` in file mode. Every date now goes through one `formatDate()`, which reads local components rather than converting to UTC.
- **Absent text.** A CSV blank is `""` and PostgreSQL returns NULL. `project()` now pins both to `null`, so `row.keyword_id ?? "none"` cannot mean two different things in the two modes.

### Verification the repository was missing

- Added `script/verify_dashboard_parity.mjs`, the Node replacement for the deleted Python parity command. It probes the two modes in separate child processes, because the mode is cached after the first read; compares row order positionally rather than as a set; reports every difference rather than the first; and lists the fields the relational schema legitimately does not carry, so the exemption is explicit and a new absence is still a failure.
- Added `dashboard/tests/dashboard.test.js`, twenty-seven tests that need no database. The three defects above are each covered by a test that fails on the original code, and `formatDate()` is tested directly against a `Date` object because file mode never produces one.
- Corrected `dashboard/vite.config.js`, whose `manualChunks` object form failed the build under Vite 8: Rolldown accepts only the function form and does not normalise the object.
- Added `node_modules/`, the two client build directories, and the generated snapshot to `.gitignore`; none had an entry, so all four would have been committed.

### Repository rules

- Rewrote the project-root `.gitignore` as the single ignore list the project owns, with the Node and build patterns written unanchored so they apply to every package in the tree rather than to one named directory, and removed `docs/.gitignore` into it. Anchoring is now reserved for rules genuinely specific to one location. `**/.vitepress/cache/` and `**/.vitepress/dist/` carry an explicit `**/` prefix, because a pattern containing a slash is anchored to the directory holding the ignore file and would otherwise match only at the top level. No tracked file changed state.
- Added an **Ignore rules** section to `AGENTS.md` recording that policy, and that a build output, an installed dependency tree, or a generated data file is never committed.
- Added a **Media handling** section to `AGENTS.md`. Media stay tracked; what the rule governs is how an agent reads them. Reading several images into one context window exhausts it and terminates the session, so an agent reads at most one at a time, prefers a listing, size, hash, or text extraction where that answers the question, and verifies a rendered page with a textual probe rather than a set of screenshots.
- Extended the work-log rules: the commit message and the work-log entry are proposed together in one request and confirmed once, because both describe the same change set and reviewing them side by side is what shows they agree. The confirmed entry is staged with the change set and committed in the same operation rather than in a follow-up, and confirmation to commit is not confirmation to push.

### Documentation

- Rewrote `docs/en/dashboard/index.md` for the Vue stack, with a `## Source Files` entry covering every file under `dashboard/`, and recorded the row-order rule in `docs/en/datasets/dashboard-data-model.md` as a constraint the schema's surrogate keys exist to satisfy.
- Consolidated versions 0.9.3 and 0.9.4 into one archived page to retain the ten-page version-log limit.

## Verification

- `node script/verify_dashboard_parity.mjs` reports all ten loaders returning identical fields, values, and row order against the live PostgreSQL instance. Before the fixes it reported 1,281 differences across four loaders.
- `npm test` in `dashboard/` passes 27 tests. Reverting each of the three parity fixes individually was confirmed to fail its own test.
- All six views were rendered in a real browser in three deployments — the API against PostgreSQL, the API against the committed files, and the static build served with no API behind it — with no console error, no failed request, and no error card in any of the eighteen renders.
- `node script/build_pages_site.mjs` assembled `site/` at 411 files and 38.9 MB; serving it resolved the dashboard at the root, the snapshot at `/data/snapshot.json`, and the documentation at `/docs/`.
- `dashboard\run.bat 8602`, run from a directory outside the repository, served both the client and the API against the live database.
- Both launchers were run against a simulated clean clone — `node_modules` and `dist` removed — on Node 26.5 and on Node 22.11. The 26.5 run installed, built, and served the client and the API; the 22.11 run is what exposed the version-floor and `npm --prefix` defects, and after the fix it is refused at step one with the range named. Every argument path was checked for its exit code in both scripts: `--help` and `-h` exit 0, an unrecognised argument and an out-of-range port exit 2, and a failed step exits 1. The failure report was confirmed to carry the version, commit, OS, Node, npm, requested port, failed step, and the last twenty lines of `dashboard/.run.log` — including the real `npm error code ENOTCACHED` from an install forced to fail.
