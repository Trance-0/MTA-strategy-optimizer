# Version 0.9.29

Date: 2026-08-26

## Changes

- Added `deploy/docker/`, which runs the Vue client and the Flask API as two containers rather than the one image AppStack deploys, so each can be rebuilt, restarted, and read on its own. `run.sh` and `run.bat` read the repository-root `VERSION` into `PROJECT_VERSION` and tag both images with it, so bumping `VERSION` is the only thing that rolls the tag and the two cannot disagree. `up` stops the previous run first: a rebuilt image does not replace a container that is already running, and the old one still holds the published ports.

- Made the data source detected rather than configured. `compose.yaml` layers a tracked `defaults.env` — `DATABASE=false` and empty `PG_*` — under the optional repository-root `.env`, last value winning, so a clean checkout with no `.env` starts and serves the committed CSV and JSON files while a configured checkout reaches its database with no extra step. The root file is passed to the **API container only** and only at run time; `.dockerignore` keeps it out of the build context, so no credential is baked into an image layer. `run.sh` prints which source resolved, because a stack reading the wrong one was previously visible only as an empty chart.

- Removed the Node server component from the dashboard. `dashboard/server/` had been documented as a parity fixture since the Flask migration and no client module imported it, but it still carried `express`, `pg`, and `dotenv` and a second implementation of the settings and CSV contracts. It is deleted along with `script/verify_dashboard_parity.mjs`, the `start` and `verify:parity` scripts, and the three runtime dependencies. `dashboard/package.json` now declares Vue and Plotly and nothing else: the client is a browser application with no database code and no `.env` of its own.

- Ported the coverage that would otherwise have been lost with it. `backend/tests/test_coercion.py` and `backend/tests/test_settings.py` hold what the Node suite proved about the CSV reader and the `.env` writer — the description-row marker, the byte-order mark, quoting and CRLF, in-place key replacement, the bounded diagnostic log — and add a case the Node suite did not cover: a password containing `=`. The backend suite went from fifteen tests to thirty-two; the dashboard suite kept its twenty-six client-only tests, two of which now read the Python source that owns the contract.

- Fixed a defect that made every database-mode snapshot fail. `backend/repository/research.py` built the compatibility keys with a literal `':IMPRESSION'` inside a `text()` statement, and SQLAlchemy reads a bare `:NAME` as a bind parameter even inside a quoted SQL literal, so `/api/dashboard` answered "A value is required for bind parameter 'IMPRESSION'" before a single row was read. Escaping it as `\:IMPRESSION` leaves PostgreSQL receiving the same string.

## Verification

- Both containers reach `healthy`, and the stack was driven in a real browser against the live PostgreSQL instance: all six views render with database rows, and there are zero console, page, or network errors. `/api/dashboard` returns its fifteen keys through the NGINX proxy in both modes — 51.7 megabytes from the database, which is what proves the bind-parameter fix under real load rather than in isolation.

- The no-`.env` fallback was verified by resolving the stack from a directory that has none: `DATABASE` comes back `false` with empty `PG_*` and no error, and the API image run with `defaults.env` alone reports `use_database False`.

- Thirty-two backend tests and twenty-six dashboard tests pass, and `npm run build` succeeds after the dependency removal.

## Known Gaps

- The whole root `.env` reaches the API container, including keys the application never reads. Deployment-only secrets belong in `deploy/.env`, which this stack does not pass.
